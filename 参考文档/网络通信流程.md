## 网络通信整体流程说明

本文档说明 ULife 项目中 **iOS 客户端 ⇄ 后端服务** 的整体通信方式，包括 JSON 接口与 Protobuf 接口两条链路，以及 AI 聊天模块的请求路径。

---

## 一、总体架构

- **客户端**：`ULife` iOS App（Swift）
  - 统一配置后端地址：`APIConfig.baseURL = "http://localhost:3000/api"`
  - 将业务接口拆分为两类：
    - **JSON + REST 接口**：通过 `NetworkManager` 调用
    - **Protobuf 接口**：通过 `ProtoNetworkManager` 调用
- **后端**：`campus_backend-main`（Rust + Axum）
  - 所有接口统一挂在 `/api` 前缀下
  - 再按模块划分路由：`/v1/users`、`/v1/forum`、`/v1/activities` 等 JSON 接口，以及 `/v1/proto/...` 的 Protobuf 接口
  - AI 聊天模块走 Protobuf 路由：`/v1/proto/ai/*`

后端入口参考 `campus_backend-main/src/main.rs`：

- 初始化数据库连接池 `get_db_pool()`
- 构建 `api_routes`：
  - JSON：`user_routes`、`course_routes`、`bbs_routes`、`activity_routes`
  - Protobuf：`user_proto_routes`、`course_proto_routes`、`bbs_proto_routes`、`ai_proto_routes`
- 通过 `Router::new().nest("/api", api_routes)` 对外提供服务

## 二、JSON 请求链路（以论坛/活动等模块为例）

### 1. 客户端侧：`NetworkManager`

- 核心职责：
  - 维护 `URLSession` 与超时时间
  - 管理全局 Bearer Token（`Authorization: Bearer <token>`）
  - 统一封装 JSON 请求、解析通用响应包裹结构 `APIResponse<T>`：
    - `code`: 业务状态码（约定 200 为成功）
    - `message`: 文本说明
    - `data`: 具体业务数据

- 关键方法：
  - `request<T: Decodable>(endpoint:method:parameters:body:)`：
    1. 拼接完整 URL：`APIConfig.baseURL + endpoint`
    2. 若为 `GET` 且携带 `parameters`，转为 query string
    3. 设置 `Content-Type: application/json` 与 `Authorization` 头
    4. 如有 `body`，使用 `JSONEncoder` 序列化为 `httpBody`
    5. 发送请求，获取 `(data, response)`
    6. 校验 HTTP 状态码：
       - 若非 2xx，优先尝试解析为 `APIResponse<String?>` 或通用 JSON 字典，提取 `code`/`message`，包装为 `NetworkError.serverError`
    7. 对 2xx 响应再解析为 `APIResponse<T>`：
       - 当 `code == 200 && data != nil` 时返回 `data`
       - 否则抛出 `NetworkError.serverError(code, message)`

- 错误统一映射为 `NetworkError` 枚举：`invalidURL` / `noData` / `decodingError` / `serverError` / `unknown`，方便 UI 做统一提示。

### 2. 服务端侧：JSON 路由

- Axum 模块如 `modules/bbs/controller.rs`、`modules/activity/controller.rs`（此处略）会：
  - 接收 JSON 请求体
  - 走数据库逻辑
  - 返回统一格式：

```json
{
  "code": 200,
  "message": "ok",
  "data": { ... }
}
```

- 返回格式与 `参考文档/通用接口.md` 中描述完全一致，保证 `NetworkManager` 能用 `APIResponse<T>` 解包。

## 三、Protobuf 请求链路（论坛 Protobuf & AI 聊天）

### 1. 客户端侧：`ProtoNetworkManager`

- 职责与 `NetworkManager` 类似，但面向 Protobuf：
  - `Content-Type` / `Accept` 设置为 `application/x-protobuf`
  - 请求/响应体使用 Protobuf 序列化（`SwiftProtobuf`）：
    - 请求：`request.serializedData()` -> `httpBody`
    - 响应：`ResponseType(serializedBytes: data)` 反序列化
  - 维护同一套 `authToken` 逻辑，统一走 `Authorization: Bearer <token>`
  - 对非 2xx 状态码，尝试直接把响应体按 UTF-8 解释为字符串，作为错误 message 抛出 `NetworkError.serverError`。

- 核心方法：
  - `requestProto<RequestType: Message, ResponseType: Message>(endpoint:method:request:retryOnNetworkLoss:)`：
    1. 拼接 URL：`APIConfig.baseURL + endpoint`
    2. 填充 HTTP 头 & Bearer Token
    3. 若有 `request`，写入 Protobuf 二进制数据
    4. 使用 `URLSession` 发送请求
    5. 对 2xx 响应二进制数据直接用目标 Protobuf 类型解析
    6. 对网络连接中断错误（`URLError.networkConnectionLost`）进行一次轻量重试

- 使用示例：`ForumRequestProto`（论坛 Protobuf 接口）中：
  - `getBoard()`：
    - 构造 `Campus_Forum_GetBoardsRequest()`
    - 调用 `protoManager.requestProto(endpoint: APIEndpoints.protobuf.forumBoards, method: .get, request: ...)`
    - 将返回的 `Campus_Forum_GetBoardsResponse` 转换为前端的 `Board` 模型

### 2. AI 聊天模块的请求链路

#### 2.1 Protobuf 定义（`Protocol/ai.proto`）

- 主要消息：
  - `ChatMessage { string role; string content; string created_at; }`
  - `ChatRequest { optional int64 conversation_id; repeated ChatMessage messages; ... }`
  - `ChatResponse { int64 conversation_id; ChatMessage reply; optional ChatUsage usage; ... }`
  - `ChatHistoryRequest` / `ChatHistoryResponse`：用于查询历史会话

客户端和服务端均由该文件生成对应的语言绑定：

- iOS：`ULife/Models/Proto/Protocol/ai.pb.swift`
- Rust：`campus_backend-main/src/proto/campus.ai.rs`

#### 2.2 iOS 调用流程（以发送一条 AI 聊天消息为例）

以 `AIChatViewController` 中 `sendMessage()` 为例：

1. 用户在输入框中输入文本，点击「发送」。
2. 控制器将文本包装为 `Campus_Ai_ChatMessage`：
   - `role = "user"`
   - `content = 用户输入`
3. 构造 `Campus_Ai_ChatRequest`：
   - 若本地已有 `conversationId`，则填入 `conversationID` 字段，否则为空表示新会话
   - `messages = [上一步构造的 ChatMessage]`
4. 调用 `AIAssistantService.shared.chat(request:)`：
   - 内部通过 `ProtoNetworkManager.requestProto`，请求路径：`/v1/proto/ai/chat`
5. 后端返回 `Campus_Ai_ChatResponse`：
   - 包含新/旧 `conversation_id`
   - `reply` 字段为 AI 助手回复的 `ChatMessage`
6. 客户端更新：
   - 将 `conversationId` 持久化到 `UserDefaults`，以便后续续写
   - 将 `reply.content` 追加到本地 `messages` 数组并刷新 `UITableView`

历史消息加载流程类似：

1. 打开页面时，如果本地存在 `conversationId`，则调用 `AIAssistantService.shared.history(conversationId:)`。
2. 该方法通过 Protobuf 请求 `/v1/proto/ai/history/{conversation_id}`。
3. 后端返回 `ChatHistoryResponse`，包含该会话的所有 `ChatMessage` 列表。
4. 客户端将其转换为内部 `ChatItem` 列表用于展示。

> 特殊处理：
>
> - 若发送请求时后端返回 404（会话不存在或已被清理），`AIChatViewController` 会将本地 `conversationId` 置空并自动重试一次，以透明方式为用户创建新会话。

#### 2.3 后端处理流程（`modules/ai`）

1. **路由层 `controller_proto.rs`**：
   - `/v1/proto/ai/chat`：
     - 使用 `ChatRequest::decode(body)` 解析 Protobuf 请求体
     - 从认证中获取用户 ID（当前暂用占位 `"test_user_id"`）
     - 调用 `AIService::chat(pool, user_id, &request)`
   - `/v1/proto/ai/history/:conversation_id`：
     - 构造 `ChatHistoryRequest` 并调用 `AIService::history(pool, user_id, conversation_id)`
   - 将 `ChatResponse` / `ChatHistoryResponse` 编码回 Protobuf 并设置 `Content-Type: application/x-protobuf`

2. **服务层 `service.rs`（`AIService::chat`）**：
   - 校验 `messages` 非空
   - 根据 `.env` 中配置的 `AI_MODEL` 构建上游 LLM 客户端（SiliconFlow OpenAI 兼容接口）
   - 若 `conversation_id` 为空：
     - 创建新会话记录 `ai_conversations`，标题取首条 user 消息前 32 字符
   - 将当前请求中的所有 `ChatMessage` 写入 `ai_messages` 表
   - 从数据库读取该会话的完整消息历史，按时间排序，构建 `upstream_messages`：
     - `assistant` → `ChatCompletionRequestAssistantMessage`
     - 其他（主要是 `user`）→ `ChatCompletionRequestUserMessage`
   - 在最前插入一条 system 提示，限定模型行为
   - 调用上游 `client.chat().create(...)` 获取回复
   - 将回复写回 `ai_messages`，并把用量统计映射为 `ChatUsage`
   - 构造 `ChatResponse` 返回（包含 `conversation_id`、`reply`、`usage`、`model`、`request_id`）

3. **历史接口 `AIService::history`**：
   - 校验用户与会话归属
   - 查询 `ai_messages`，按时间顺序返回 `ChatMessage` 列表

## 四、鉴权与环境配置

### 1. 鉴权方式

- 所有需要登录的接口（无论 JSON 还是 Protobuf）都通过 `Authorization: Bearer <token>` 进行鉴权：
  - 客户端登录成功后，从登录接口拿到 token
  - 调用 `NetworkManager.setAuthToken` 和 `ProtoNetworkManager.setAuthToken` 进行保存
  - 后续所有请求都会自动在 Header 中携带该 token

### 2. 环境配置

- 客户端：
  - `APIConfig.baseURL` 指向后端网关地址，例如开发环境为 `http://localhost:3000/api`
  - `APIConfig.timeout` 控制请求超时时长

- 后端（`.env`）：
  - 数据库连接 `DATABASE_URL`
  - AI 聊天模块：`SILICONFLOW_API_KEY`、`SILICONFLOW_BASE_URL`、`AI_MODEL` 等（详见 `AI助手模块.md`）

---

## 五、总结

- **数据格式层**：
  - 业务 JSON 接口统一走 `APIResponse<T>` 包裹结构
  - 性能敏感/强类型模块（如论坛列表、AI 聊天）采用 Protobuf 以减少体积、提升解析效率
- **网络层**：
  - iOS 端通过 `NetworkManager` 与 `ProtoNetworkManager` 实现两种数据格式的统一收口
  - 后端通过 Axum 模块化路由，将 JSON 与 Protobuf 接口分别挂在 `/v1/*` 与 `/v1/proto/*`
- **业务层**：
  - 各功能模块（论坛、活动、课表、AI 聊天等）只关注自身 DTO/Proto 的拼装与结果解析，底层通信细节被网络层完全屏蔽，方便后续扩展或替换实现。
